# Handoff: Compiling `wp-block-guard` to a Bun v1.4 Single-File Executable

**Date:** 2026-09-03
**Scope:** Research only — no code in this repo was changed to produce this document.
**Subject:** feasibility of `bun build --compile` for `wp-block-guard` (Node ESM CLI, deps `block-runner@^0.8.0` + `fast-glob@^3.3.3`).

---

## Verdict

**Feasible, but only with one specific architectural change, and it is not the one the current code uses.** The crux is item 3 below: `src/block-runner-adapter.js` currently resolves `block-runner`'s own `dist/cli.js` off disk via `require.resolve('block-runner/package.json')` and spawns it as a brand-new OS process with `node:child_process.spawn`. Inside a `bun build --compile` binary, everything block-runner needs (its own code, `@wordpress/blocks`, `@wordpress/block-editor`, `@wordpress/block-library`, `jsdom`) gets pulled into Bun's embedded module graph — a virtual filesystem (`/$bunfs/...`, `B:\~BUN\...` on Windows) that a real OS process **cannot** be spawned against, because `spawn()` needs a path openable by the *OS's* loader, not Bun's. This is not a hypothetical: it is the exact failure mode documented in a real, merged fix (`coleam00/archon#990`, cited below) for a different CLI (Claude Agent SDK) hitting the identical "compiled binary must spawn a script that lives inside its own bundled dependency" problem. The good news, discovered during this research and not previously evaluated in `archive/2026-09-03-wp-gutenberg-validator-cli-design.md`, is that `block-runner`'s published package **already exposes a real JS library API** (`exports: { ".": "./dist/index.js" }`, with a typed `validate()`/`convert()`/`fix()`-equivalent function set) — so the fix is not "extract the CLI to a temp file," it's "stop spawning a CLI at all and import the library in-process." That converts the hard problem (subprocess-across-a-virtual-filesystem) into an easier, still-nonzero one (does block-runner's in-process dependency stack — jsdom 29.1.1 + `@wordpress/blocks`/`block-editor`/`block-library` — run correctly when bundled and executed by Bun's JavaScriptCore-based runtime instead of Node's V8). Evidence found here suggests jsdom-under-Bun is broadly workable, but this specific dependency combination has not been proven and must be empirically verified before committing to this path (see Open Questions).

## Findings

### 1. Exact current syntax/capabilities of `bun build --compile` (Bun v1.4)

**Primary source, bun.com/docs/bundler/executables** (fetched live, current docs; this page is versionless/rolling but reflects the current release):
- "Bun's bundler implements a `--compile` flag for generating a standalone binary from a TypeScript or JavaScript file." Basic invocation: `bun build --compile ./path/to/entry.ts --outfile myapp`.
- Default output: if no `--outfile` is given, "the executable is named after the entrypoint and written to `outdir`, or to the current working directory."
- Dependency scope: "Bun bundles all imported files and packages into the executable, along with a copy of the Bun runtime." — i.e. everything statically or dynamically `import`ed, not necessarily the *entire* `node_modules` tree of unrelated packages, but the full transitive closure of what the entry point actually imports.
- Windows extension handling, per `docs/bundler/executables.mdx` (GitHub, same content mirrored at bun.com): "note: if no .exe extension is provided, Bun adds it automatically for Windows executables."
- Windows-only metadata flags (icon/title/publisher/version/description/copyright) "can't be used when cross-compiling because they depend on Windows APIs" — this is a real Windows-specific caveat, source: bun.com/docs/bundler/executables.
- Source: <https://bun.com/docs/bundler/executables>, mirrored at <https://github.com/oven-sh/bun/blob/main/docs/bundler/executables.mdx>.

**v1.4-specific change relevant here — primary source:** `oven-sh/bun#25934` (merged PR, Jan 9 2026): adds `--compile-executable-path <STR>`, letting `--compile --target=bun-linux-x64 --compile-executable-path=/path/to/bun-linux-x64` supply a custom Bun runtime binary instead of downloading one from the npm registry during cross-compilation — mainly relevant for offline/airgapped or CI-cached builds, not needed for a same-OS build on Windows. Source: <https://github.com/oven-sh/bun/pull/25934>.

**Also relevant, not v1.4-specific but current:** full-stack executables (bundling frontend assets via HTML imports) landed in Bun v1.2.17 — irrelevant to this CLI (no HTML/browser assets) but confirms the compile feature has kept expanding rapidly across releases, so version-pinned claims should always be re-checked. Source: `docs/bundler/executables.mdx` "Full-stack executables" section, <https://github.com/dokob0512/bun/blob/259f16f49f0ad65ac97931bfac4cfa4fdcfb67dc/docs/bundler/executables.mdx> (mirror of the same official doc content).

**Bun v1.4 release itself:** "Bun 1.4 adds +1,517 tests from the Node.js test suite — our biggest jump in Node.js compatibility since Bun 1.0. Bun v1.4 also fixes over 2,900 issues." Source: <https://bun.com/blog/bun-v1.4>. This is general runtime compatibility, not `--compile`-specific, but it directly bears on item 6.

### 2. Cross-platform / cross-compilation support

**Primary source — target list, `docs/bundler/executables.mdx`:** supported `--target` values are `bun-linux-x64`, `bun-linux-arm64`, `bun-linux-x64-musl`, `bun-linux-arm64-musl`, `bun-windows-x64`, `bun-windows-arm64`, `bun-darwin-x64`, `bun-darwin-arm64`. The `bun-` prefix is mandatory: `oven-sh/bun#23899` (closed, fixed) is a filed-and-fixed doc bug where the official blog post (bun.com/blog/bun-v1.3#cross-compile-executables) originally showed bare names like `--target=linux-x64`, which actually throws `InvalidTarget` — confirmed by the maintainer's own reply "Thanks, fixed!". Always use the `bun-`-prefixed form. Source: <https://github.com/oven-sh/bun/issues/23899>.

**Building ON Windows for the Windows target itself (the case that matters here — no cross-compile needed):** this is the well-trodden, native path and no issues specific to it were found in the index; the cross-compile bug reports below are all about compiling *to a different OS* than the host.

**Cross-compiling FROM Windows (if ever needed for CI/Linux artifacts) — primary-source-confirmed bugs, some fixed, some still open as of the index's last crawl:**
- `oven-sh/bun#12496` / `#12797` (Bun v1.1.18/1.1.20): "panic when cross compiling to linux on Windows" — an internal assertion failure (`moveFileZ` / `downloadToPath`), reproduced by two independent reporters, tracked as fixed by `oven-sh/bun#12862` ("fix(build): assertion failure when cross-compiling on windows"). Notably, both original reports reproduce specifically "only if compiling from a drive other than the system drive (i.e. other than C:)" — a very Windows-specific footgun.
- `oven-sh/bun#25346` (Bun v1.3.3, filed Dec 2025, marked duplicate of `#11198`): `Failed to extract executable for 'bun-linux-x64-v1.3.3'. The download may be incomplete.` when cross-compiling from Windows. A commenter's workaround, confirmed by the reporter: "making a test project on the C: drive did fix it" — i.e. the non-system-drive bug from `#12496` appears to recur across versions and is a live, not fully eradicated, class of Windows-cross-compile flakiness.
- `oven-sh/bun#10740`: "Cross-compile crash when building Linux executable on Windows" with `--minify --sourcemap`, another distinct crash report.
- Given `wp-block-guard`'s only target is Windows itself (no stated need to cross-compile to Linux/macOS from this Windows dev machine), these bugs are **not blocking** but are worth knowing about if CI later cross-builds Linux/macOS artifacts from a Windows runner.
- Sources: <https://github.com/oven-sh/bun/issues/12496>, <https://github.com/oven-sh/bun/issues/12797>, <https://github.com/oven-sh/bun/issues/25346>, <https://github.com/oven-sh/bun/issues/10740>.

**Building Bun itself on Windows** (not relevant to this project — this project only needs the pre-built `bun` CLI, not to compile Bun from source) is documented at <https://bun.com/docs/project/building-windows> and requires Visual Studio, LLVM 21.1.8, Rust, Go, NASM, etc. — noted only to avoid confusing "building Bun" with "using `bun build --compile`," which requires none of that.

### 3. Can a compiled executable spawn a separate file from its own bundled dependencies? (the crux)

This is the single most important finding and it is unambiguous, primary-source-confirmed, and directly analogous to `wp-block-guard`'s design.

**Embedding mechanism, primary source (`docs/bundler/executables.mdx` / bun.com):** "Bun bundles all imported files and packages into the executable" — as an embedded virtual filesystem, referred to across Bun's own PRs and issues as `/$bunfs/root/...` (POSIX) or `B:\~BUN\root\...` (Windows). This is confirmed by multiple merged PRs that had to teach individual Bun APIs (`Glob.scan`, `Bun.serve` directory routes) to read from this virtual table instead of the real filesystem — e.g. `oven-sh/bun#40937` (merged): "In a compiled executable, `Glob.scan` and `Glob.scanSync` fail with `ENOENT: no such file or directory, open '/$bunfs/root/build'` (`B:\~BUN\root\build` on Windows), while `fs.readdir` lists the same embedded directory... A compiled executable embeds its assets in the standalone module graph: a process-lifetime table of files and directory prefixes keyed by virtual posix paths under `/$bunfs/root/`." Source: <https://github.com/oven-sh/bun/pull/40937>.

**Directly on-point precedent — a compiled binary needing to spawn a script from its own bundled npm dependency:** `coleam00/archon#990` (merged PR) fixes exactly this class of bug for the Claude Agent SDK inside a `bun build --compile` binary:
> "Fixes a P0 bug in v0.3.1 where every compiled binary fails to spawn Claude with `Module not found "/Users/runner/.../node_modules/.bun/@anthropic-ai+claude-agent-sdk@.../cli.js"`... In a `bun build --compile` binary, `import.meta.url` of a bundled module is **frozen at build time** to the absolute path where that module lived on the build host... Every shipped binary carried the CI path, and every workflow run hit `spawn ENOENT`... **The SDK ships a dedicated `@anthropic-ai/claude-agent-sdk/embed` entry point built for exactly this case.** It uses `import cli.js with { type: 'file' }` so Bun's bundler embeds `cli.js` into the compiled binary's `$bunfs` virtual filesystem, then `extractFromBunfs()` copies it to a real temp path at runtime (**child processes cannot read the parent's `$bunfs`**). We import that entry point and pass the result as `pathToClaudeCodeExecutable`."

This confirms, from a real shipped fix: (a) `require.resolve`/`import.meta.url`-based path resolution to a dependency's CLI script silently breaks in a compiled binary because the resolved path reflects the *build machine's* filesystem, not the runtime machine's, and even where it happens to resolve, (b) the resolved location is inside `$bunfs`, which a spawned OS child process categorically cannot open — confirming the task's hypothesis exactly. The general-purpose fix pattern used here (`with { type: 'file' }` import attribute + an explicit runtime extraction step to a real temp file before spawning) is Bun's own documented mechanism for this exact situation.
Source: <https://github.com/coleam00/archon/pull/990>.

**`Bun.embeddedFiles` API, confirmed via a second independent project's build-migration doc** (`backlog.md` / `mrlesk/backlog.md`, doc dated as a completed task in that repo): "Use Bun's native `Bun.embeddedFiles` API for accessing embedded assets... Access embedded files via `Bun.embeddedFiles` array of Blob objects." This corroborates the official docs' `with { type: "file" }` + `Bun.embeddedFiles` mechanism from a second, independent real-world usage. Source: <https://github.com/mrlesk/backlog.md/blob/944faf93fd25a9048773d65933e9258db4b1f186/backlog/completed/back-100.7%20-%20Bundle-web-assets-into-executable.md>.

**Long-standing, still-relevant upstream feature request confirming this is a known ecosystem-wide gap, not a `wp-block-guard`-specific problem:** `oven-sh/bun#9392`, "Support for a virtual filesystem in the style of `@yao-pkg/pkg` for a single file executable" (open since Mar 2024, still referenced in the index). A maintainer reply (Jarred-Sumner) says "You can embed files in `bun build --compile` if you explicitly import them," to which a commenter (segevfiner) presses the actual unsolved case: "The question is how you will get it to work with arbitrary npm packages that use Node.js `fs` to read files from inside the package, like `pkg` handles." Another commenter (Exitium-DEV) asks the *exact* question this project faces: "How does one spawn a subprocess of an embedded file?" — with the maintainer's only answer being "you can use fs.readFile" (i.e., read the embedded bytes yourself and write them to a real path — there is no built-in "spawn this embedded file" primitive). Source: <https://github.com/oven-sh/bun/issues/9392>.

**Conclusion for item 3:** Bun does **not** support spawning an embedded file directly. The documented, working pattern (proven by a real merged fix in a comparable CLI) is: import the target file with `with { type: 'file' }` so it lands in `Bun.embeddedFiles`/the bunfs graph, then at runtime read its bytes and write them to a real temp-directory path before calling `spawn()`/`Bun.spawn()` against that real path. This is mitigation (b) in the task's list, and it is real and workable — but for `wp-block-guard`, mitigation (a) (drop the subprocess entirely) is available and strictly better because it removes the whole problem instead of working around it (see the Architectural Risk section).

**Correction to an earlier draft of this document:** an initial pass here relied on a WebFetch summary of `block-runner`'s registry `exports` field that omitted a subpath entry, which appeared to contradict `src/block-runner-adapter.js`'s own comment that `"block-runner/package.json"` "*is* exported." The on-disk `node_modules/block-runner/package.json` (read directly, not summarized) settles it — the real `exports` map is:
```json
"exports": {
  ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js", "default": "./dist/index.js" },
  "./package.json": "./package.json"
}
```
So the adapter's comment was correct all along; the discrepancy was an artifact of an intermediate summarization step in this research pass, not a real inconsistency in block-runner. Noted here as a reminder that registry-API summaries (including in this same document, elsewhere) should be treated as lower-confidence than a direct file read wherever the actual file is available.

Source: `https://registry.npmjs.org/block-runner/latest` (npm registry API, live fetch, 2026-09-03).

**jsdom-under-Bun, runtime (not compile) compatibility — anecdotal/community, not from Bun's own issue tracker directly, but from a documentation source with a compatibility matrix:** a testing-library integration doc (`wellwelwel/poku`) states a runtime × DOM-adapter matrix with `jsdom` marked ✅ for both Node.js ≥20 and Bun ≥1, with only Deno flagged unstable. Source: <https://github.com/wellwelwel/poku/blob/e02df0b6d55f02a687c038a9d404d179405bd048/website/docs/documentation/plugins/official/react.mdx>. This is a third-party compatibility claim, not an official Bun statement, but it is a maintained library's stated support matrix rather than a blog opinion, so treat it as **moderate-confidence, not primary-source-confirmed for this exact jsdom version (29.1.1)**.

**A concrete counter-signal worth flagging:** a real migration doc (`udecode/plate`, Slate/React test-suite Bun migration) found a specific DOM-fidelity mismatch: "Bun + Happy DOM returned the old `"test"` node instead of `"bar"`... Bun + an ad hoc JSDOM preload also failed, but with `"foobar"` instead of `"bar"`," for a focus/selection-sensitive test, and the fix was to **not** use Bun's runtime for that lane and fall back to Vitest + jsdom 20.0.3. This shows jsdom-under-Bun is not always bit-for-bit identical to jsdom-under-Node for behaviorally subtle DOM operations. Source: <https://github.com/udecode/plate/blob/12a034f7cfe698cc020fade0d4849373d6faa065/docs/solutions/test-failures/2026-04-17-slate-react-focus-tests-need-vitest-jsdom-20-not-happy-dom-or-jsdom-26.md>. `block-runner`'s use of jsdom is for headless block `save()` rendering/diffing, not interactive focus/selection, so this specific mismatch class is likely irrelevant — but it establishes that "jsdom basically works under Bun" is not the same claim as "jsdom behaves identically under Bun for all operations."

**React/`react-dom` under Bun — primary source, a real, still-relevant compatibility bug:** `facebook/react#28941` (closed, but instructive): "In the exports field of `react-dom`'s package.json, there is no 'bun' field. Bun defaults to the 'default' field... the `./server.node.js` file doesn't export `renderToReadableStream()`... `SyntaxError: Export named 'renderToReadableStream' not found in module`." Resolution, per maintainer `gnoff`: fixed properly in React 19 (which added a `bun` export condition); for React 18, the workaround is to import from `react-dom/server.browser` explicitly. Bun's own official SSR doc (`docs/guides/ecosystem/ssr-react.mdx`) confirms this is a known, documented gotcha: "If you run into an error like `export named 'renderToReadableStream' not found`, please make sure to install version `19` of `react` & `react-dom`, or import from `react-dom/server.browser` instead of `react-dom/server`." Sources: <https://github.com/facebook/react/issues/28941>, <https://github.com/oven-sh/bun/blob/259f16f49f0ad65ac97931bfac4cfa4fdcfb67dc/docs/guides/ecosystem/ssr-react.mdx>. **This is squarely relevant**: `@wordpress/element` wraps React/`react-dom`, and if `@wordpress/block-editor`'s transitive React version is 18.x and block-runner (or its transitive deps) imports `react-dom/server` (not `.browser`) for its headless `save()` execution, this exact export-resolution failure could occur when block-runner runs under Bun instead of Node — but only if block-runner actually uses SSR-style `react-dom/server` rendering internally, which was not confirmed from block-runner's own source in this pass (its `dist/` is compiled/bundled, and this class of bug can be masked or exposed differently depending on how the bundler resolved the import at block-runner's own build time). **Flagged as an open question requiring empirical testing**, not resolved by documentation alone.

### 5. Startup-time and distribution-size evidence

**Official Bun benchmarks:** none were found specifically quantifying `--compile` startup time/size in the primary docs; the docs describe the feature functionally, not with benchmark numbers.

**Anecdotal/web-sourced (explicitly not primary-source, treat as illustrative only):**
- A public, methodologically-described community benchmark repo, `yyx990803/bun-vs-node-sea-startup` (maintained by Vue.js creator Evan You), compares `bun build --compile` against Node's Single Executable Applications (SEA) feature on a synthetic "500 modules, 7000 functions, 12 structurally distinct code shapes" TypeScript project, 30 iterations, macOS arm64:
  | Approach | Mean startup | Binary size |
  |---|---|---|
  | Bun compile + bytecode | 111.0 ms | 83.0 MB |
  | Node SEA + code cache | 139.7 ms | 117.1 MB |
  | Node SEA standard | 161.3 ms | 114.7 MB |
  | Bun compile (no bytecode) | 189.9 ms | 60.2 MB |

  Notable: plain `bun build --compile` (no `--bytecode` flag) is the *smallest* binary here (60.2 MB) but *slower to start* (189.9 ms) than Node SEA with code caching — the bytecode-compilation variant is what wins on speed, at the cost of a larger binary (83 MB, +23 MB over the non-bytecode build). For `wp-block-guard`, which bundles `@wordpress/blocks`/`block-editor`/`block-library` + jsdom + React transitively, expect a binary in a similar tens-of-MB range once block-runner's dependency tree is included — this synthetic benchmark's "500 modules" is a reasonable proxy for a React-adjacent WordPress dependency tree, but it is a *different* codebase, so treat the absolute numbers as **illustrative order-of-magnitude, not a prediction for this specific project**. Source: <https://github.com/yyx990803/bun-vs-node-sea-startup> (via WebFetch summary of the repo's own README/results).
- General ecosystem claims like "Bun cold-starts at 290ms vs Node's 940ms" or "Bun startup 8-15ms vs Node 60-120ms" appearing in multiple 2026 SEO-style comparison blog posts (strapi.io, tech-insider.org, pkgpulse.com, daily.dev) are **unattributed, inconsistent with each other, and not sourced to any reproducible benchmark** — do not cite these as evidence; they are marketing-adjacent content, included here only to note that the "Bun is fast" narrative is broadly repeated but the specific numbers in circulation do not agree with one another or clearly describe `--compile` specifically (vs. plain `bun run`/module resolution speed, a different metric).

## Architectural risk: block-runner's subprocess model under a compiled executable

**What currently happens (`src/block-runner-adapter.js`):** `resolveBlockRunnerCli()` does `require.resolve('block-runner/package.json')`, reads the `bin` field (`{ "block-runner": "dist/cli.js" }` — confirmed live from npm), joins it with the package.json's directory, and `runCli()` calls `spawn(process.execPath, [cliPath, ...args], { stdio: [...] })`, piping markup over stdin and reading JSON from stdout.

**What breaks under `bun build --compile`, concretely:**
1. `require.resolve('block-runner/package.json')` inside a compiled binary resolves against Bun's embedded module graph, not a real path on the runtime machine's disk. Per the Archon precedent (`coleam00/archon#990`), the resolved value is either a `$bunfs`-style virtual path or (if the resolution mechanism instead froze an absolute build-host path, as `import.meta.url` does) a path that simply does not exist on the machine actually running the compiled `.exe`.
2. Even in the best case where the path happens to look plausible, `child_process.spawn(process.execPath, [cliPath, ...])` needs the OS's own process loader to open `cliPath` — the OS loader has no knowledge of Bun's embedded file table. Per `oven-sh/bun#9392`, there is no built-in "spawn an embedded file" primitive in Bun; the maintainer's own guidance is "you can use fs.readFile" (i.e., handle it yourself).
3. Consequence: every `validateMarkup()`/`fix` call would fail at runtime in the compiled binary with something in the family of `spawn ENOENT` or `Module not found "/$bunfs/root/..."` — the exact symptom class documented in `oven-sh/bun#10595` and fixed for a structurally identical case in `coleam00/archon#990`.

**Candidate mitigations, evaluated:**

- **(a) Import `block-runner`'s library API in-process instead of spawning its CLI.** **Ruled IN — recommended.** Confirmed by reading `node_modules/block-runner/package.json` and `node_modules/block-runner/dist/index.d.ts` directly on disk (not summarized — the actual files, since block-runner is already an installed dependency of this repo):
  - `package.json`'s `exports` map: `{ ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js", "default": "./dist/index.js" }, "./package.json": "./package.json" }`.
  - `dist/index.d.ts` declares exactly these exported functions: `canonicalize(markup, options?): Promise<BlockRunnerReport>`, `validate(markup, options?): Promise<BlockRunnerReport>`, `convert(input, options?): Promise<BlockRunnerReport>`, `extractIntent(out): IntentTree`, `assemble(nodes): Promise<WpBlock[]>`, `realize(rawIntent, options?): Promise<BlockRunnerReport>`, `collectSiteContext(options): Promise<string>` — plus the full `BlockRunnerReport`/`ReportItem`/`ReportSummary`/`SourceLocation` type set, which is **the same report shape** the current adapter already parses out of the CLI's `--json` stdout.
  - **Important correction versus an earlier draft of this section:** there is **no exported `fix()` function.** The CLI's `fix` subcommand corresponds to the library's `canonicalize(markup, options?)` — the `CommandName` type (`'validate' | 'fix' | 'convert' | 'assemble'`) names the CLI verb, but the exported function for that verb is `canonicalize`, not `fix`. Any implementation must call `canonicalize()`, not `fix()`; the latter does not exist and would fail to import.
  - `validate(markup: string, options?: ValidateOptions): Promise<BlockRunnerReport>` — takes a markup string directly (not a file path) and returns a `Promise`, which matches `validateMarkup(markup)`'s existing contract in `src/block-runner-adapter.js` almost exactly (the only change needed is `await validate(markup)` instead of spawning + JSON-parsing stdout).
  - Neither `index.d.ts` nor its exported function list expose any separate "bootstrap"/"init"/"register blocks" function alongside `validate()`. This is a meaningful finding in itself: the prior research this project's design doc cites (`WordPress/gutenberg#68695`) shows that bootstrapping `@wordpress/block-library` in plain Node requires installing jsdom globals *before* importing the block-library registration code, split across separate files "for ordering global imports." Since block-runner's public API has no equivalent caller-facing bootstrap step, block-runner must be doing this ordering internally inside `dist/index.js` before `validate()` is usable — i.e. this is self-contained today under Node, but it is exactly the kind of import-order-sensitive setup that a bundler (Bun's, doing static analysis and re-ordering/tree-shaking module graphs for `--compile`) could disturb. **This is now the primary open question for mitigation (a)** — not "does jsdom exist under Bun" in the abstract (item 4 above suggests broadly yes), but "does block-runner's specific internal jsdom-bootstrap-before-registerCoreBlocks ordering survive being bundled by Bun's bundler rather than run as authored under plain Node." See Open Questions.

  This means `wp-block-guard` can `import { validate, canonicalize } from 'block-runner'` and get the identical report shape **without spawning any process at all** — the entire item-3 risk disappears because there is no second file to spawn; block-runner's code becomes just another statically-imported dependency that Bun bundles directly into the executable like any other. This was not evaluated in the prior design doc (`archive/2026-09-03-wp-gutenberg-validator-cli-design.md`), which resolved the CLI bin purely to avoid `npx`'s ~12s cold-start overhead — a concern that also disappears with an in-process import (no process spawn at all, in-process call is sub-millisecond dispatch). The residual risk this mitigation does *not* remove is item 4/6: block-runner's own dependency stack (jsdom, `@wordpress/blocks`/`block-editor`/`block-library`, and their transitive React) must now execute correctly *inside Bun's runtime, as bundled by Bun's own bundler* rather than inside a separate `node` process — this was previously insulated by the process boundary and is no longer insulated once imported directly. This is the one piece requiring hands-on verification (see Open Questions), but it is a "does it run, in this exact bundled shape" question, not an architectural dead end, and Bun's Node-compatibility posture (item 6) plus jsdom's general Bun support (item 4) make it plausible.

- **(b) Extract the embedded block-runner CLI script to a real temp-directory file at first run, then spawn that.** **Ruled IN as viable but strictly inferior to (a) for this codebase.** This is Bun's own documented, proven pattern — `with { type: 'file' }` import attribute + `Bun.embeddedFiles`/`extractFromBunfs()`-style runtime extraction, exactly as shipped in `coleam00/archon#990`. It would work, but it (i) still pays a subprocess-spawn cost per validated file (the current design's own stated performance concern, previously solved by skipping `npx`, would partially resurface as "spawn `node`/`bun` against a temp-extracted script" per call), (ii) requires shipping/extracting not just `dist/cli.js` but its *entire* runtime dependency closure (jsdom, `@wordpress/*`, React) since a spawned child process is a fresh Bun/Node process with no access to the parent's module graph — meaning this isn't a single-file extraction, it's extracting block-runner's whole `node_modules`-equivalent tree, and (iii) needs careful temp-dir lifecycle management (extraction path, permissions, cleanup, concurrent-invocation safety) that a `forge`/`package-root.js`-style pattern found during this research (per-user cache dir keyed by version+fingerprint, atomic mkdtemp+rename, not raw `os.tmpdir()`) shows is nontrivial to get right. Given (a) exists and sidesteps all of this, (b) should only be revisited if (a) turns out to be blocked by a real, unfixable Bun/jsdom or Bun/React incompatibility.

- **(c) Ship block-runner's `dist/cli.js` and its dependency tree as a sibling file/directory alongside the compiled executable, not embedded at all.** **Ruled OUT as the primary approach.** This works mechanically (spawn a real sibling path on the real filesystem — no bunfs involved) but defeats the stated deployment goal ("simplify deployment to a single binary with no `node_modules`/npm-install step for end users"): it just relocates the `node_modules` problem next to the exe instead of inside it. Only worth considering as a fallback if (a) is blocked and (b)'s extraction complexity is judged not worth it — but even then it is a worse fit for this project's stated goals than (a).

- **(d) Whether Bun's compile step can follow a `child_process.spawn` call and auto-bundle the target script's own dependency closure (multi-entry-point compilation).** **Ruled OUT — no evidence this exists.** Nothing in Bun's docs or the issue tracker describes `--compile` following runtime `spawn()` calls to discover and bundle additional entry points; `--compile` only bundles what is statically/dynamically `import`ed by the *given* entry file (per item 1's "all imported files and packages" wording) or by the multi-entrypoint pattern the full-stack-executable feature uses for HTML/CSS/JS asset trees specifically — not for arbitrary subprocess targets. `bunup`'s own docs (a third-party build tool wrapping Bun's compile feature) state plainly: "Only one entrypoint can be compiled at a time. If you want to compile multiple entrypoints, you need to use a build config array with separate configurations" — reinforcing that Bun's compile model has no concept of "discover and bundle whatever this process might spawn later."

**Net conclusion:** mitigation (a) is the clear, evidence-backed answer. It is not merely "the least bad option" — it removes the architectural risk entirely rather than working around it, and it happens to be available because block-runner ships a real library API that the current adapter never used.

## Concrete implementation plan

1. **Library API shape is already confirmed** (this document read `node_modules/block-runner/dist/index.d.ts` directly): `validate(markup: string, options?: ValidateOptions): Promise<BlockRunnerReport>` and `canonicalize(markup: string, options?: CanonicalizeOptions): Promise<BlockRunnerReport>` are the two functions needed to replace the adapter's `validate`/`fix` CLI invocations, respectively — there is **no `fix()` export**; `fix` is a CLI-only verb name, `canonicalize()` is its library equivalent. Diff the `BlockRunnerReport`/`ReportItem`/`ReportSummary` fields (reproduced in Finding 4's evidence above) against exactly what `validateMarkup()`'s current JSON-parsing code in `src/block-runner-adapter.js` reads off CLI stdout, to confirm no field-name drift before rewriting call sites — they appear identical since the CLI's own `--json` output is presumably just `JSON.stringify()` of this same `BlockRunnerReport` type, but confirm rather than assume.
2. **Rewrite `src/block-runner-adapter.js`** to replace `resolveBlockRunnerCli()`/`runCli()`/`spawn()` with a direct `import { validate, canonicalize } from 'block-runner'`, keeping the adapter's existing external function signatures (`validateMarkup(markup)` etc.) so the rest of `wp-block-guard`'s code (`src/cli.js` and callers) needs no changes beyond the internals of this one file. **This step touches `src/`, which is out of scope for the requesting agent under this task's constraints — hand this specific change to whichever agent owns `src/` next, or do it in a dedicated follow-up task once the other background agents are done with that path.**
3. **Add a `compile` script to `package.json`:**
   ```json
   "scripts": {
     "compile": "bun build --compile ./bin/wp-block-guard.js --outfile wp-block-guard.exe"
   }
   ```
   No `--target` flag is needed for a same-machine Windows build (native host target is implicit). Only add `--target=bun-windows-x64` (or `-arm64`) if cross-compiling from a non-Windows CI runner later — and if so, budget time for the Windows-cross-compile flakiness noted in Finding 2 (`#12496`/`#25346`: build from the `C:` drive, not a secondary drive, if cross-compiling *from* Windows *to* another OS — this doesn't apply to the reverse direction, but hasn't been separately verified either).
4. **Bun must actually be present** to run step 3 — this is a new build-time tool dependency for the maintainer (not for end users of the resulting `.exe`), separate from the `node >=20` `engines` constraint already in `package.json`. Document this in the repo's build docs (README/CONTRIBUTING, not modified here since this task is research-only).
5. **Verify the resulting binary with a real smoke test**, using the existing fixtures at `tests/fixtures/wp-block-guard/` (confirmed present: `valid-heading.html`, `invalid-heading-missing-class.html`, `invalid-attrs-json.html`, `mismatched-closer.html`, `no-blocks.html`, `unbalanced-delimiter.html`, `pattern-with-header.php`, `pattern-with-interpolation.php`):
   ```sh
   ./wp-block-guard.exe validate tests/fixtures/wp-block-guard/valid-heading.html
   echo $?   # expect 0
   ./wp-block-guard.exe validate tests/fixtures/wp-block-guard/invalid-heading-missing-class.html
   echo $?   # expect 1 (or whatever the CLI's documented findings-present exit code is, per src/cli.js)
   ./wp-block-guard.exe validate tests/fixtures/wp-block-guard/unbalanced-delimiter.html
   # this exercises the "Layer 1" structural pre-check from the design doc — confirm it still
   # fires correctly now that block-runner is imported, not spawned, since that pre-check is
   # wp-block-guard's own code and should be unaffected either way
   ```
   Compare exit codes and JSON output against the equivalent `node bin/wp-block-guard.js ...` invocations on the same fixtures to confirm parity, not just "doesn't crash."
6. **Windows-specific build/run notes:**
   - Building the executable itself requires nothing beyond `bun` being installed and on `PATH` — no Visual Studio/LLVM/Rust toolchain is needed to *use* `--compile` (that toolchain is only for building the Bun *runtime itself* from source, per `docs/project/building-windows`, which does not apply here).
   - Bun auto-appends `.exe` if omitted from `--outfile` on a Windows target — harmless, but be explicit in the script to avoid ambiguity in cross-platform build scripts later.
   - If ever adding `--windows-hide-console`/`--windows-icon`/etc. metadata flags, note that most of them (icon/title/publisher/version/description/copyright) require running the compile step *on* Windows (they go through `rescle`/`BeginUpdateResourceW`, Windows-only APIs) — not an issue here since the build already happens on Windows.
7. **Do not delete the Node.js code path.** Keep `bin/wp-block-guard.js` + `src/cli.js` runnable under plain `node` as-is; the compiled `.exe` should be an additional distribution artifact, not a replacement, until the in-process block-runner integration (step 2) has real-world mileage under Bun.

## Open questions / things that need hands-on verification

1. **Does `import { validate } from 'block-runner'` actually run correctly when executed by Bun (both plain `bun run` and inside a compiled `--compile` binary)?** This is the one load-bearing unknown left after ruling in mitigation (a). Specifically: does block-runner's internal jsdom-bootstrap-before-`registerCoreBlocks()` ordering (which its public API hides from callers — see Architectural Risk, mitigation (a)) survive execution under Bun's runtime, and does whatever React version `@wordpress/block-editor@17.0.0`/`@wordpress/element` pulls in avoid the `react-dom/server` export-resolution bug (`facebook/react#28941`) that only affects React <19 under Bun. **Action:** `bun add block-runner`, then `bun run` a small script calling `validate()` on `tests/fixtures/wp-block-guard/valid-heading.html` and `invalid-heading-missing-class.html`, and diff the output against the current Node-subprocess adapter's output on the same fixtures, before touching `src/`.
2. **Does the same `validate()` call still work once the whole thing is `bun build --compile`d**, given the extra step of Bun's bundler statically resolving and embedding block-runner's own imports (jsdom, `@wordpress/*`)? This is a distinct question from #1 — bundling can surface issues (e.g. dynamic `require()`s inside a dependency that the bundler can't statically see, native-module `.node` file dependencies, or asset files a package expects to read from its own directory at runtime — jsdom in particular has historically shipped some data files) that don't appear under plain `bun run`. **Action:** actually run the full compile + smoke test in step 5 of the implementation plan rather than assuming success from #1 alone.
3. **Binary size, in practice, for this specific dependency tree.** The only size numbers found (Finding 5) are from an unrelated synthetic benchmark. **Action:** just measure `wp-block-guard.exe`'s actual size after a real compile and decide if it's acceptable for the intended distribution mechanism (this matters more if distributing via something size-constrained, e.g. an npm postinstall download or a git-tracked binary).
4. **`fast-glob`, low risk:** it walks real on-disk paths the user supplies via Node's own `fs`/`readdir`, not `Bun.Glob`, so the `Glob.scan`-under-bunfs bug class (`oven-sh/bun#40937`) does not apply to it. Worth a smoke-test pass but not a design concern.
